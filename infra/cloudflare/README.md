# Cloudflare Infrastructure

This directory manages Atlas IT Cloudflare configuration, including the ruleset that blocks `/app` on the production zone and the Zero Trust Access applications and policies for the development and staging domains.

## Prerequisites
- Terraform >= 1.5
- Cloudflare provider >= 5.0 (pinned via `required_providers`)
- Cloudflare API token with permissions for Rulesets and Zero Trust Access

## Variables
| Name | Type | Description |
| --- | --- | --- |
| `api_token` | `string` | Cloudflare API token passed to the provider. Use a scoped token (Rulesets + Access). |
| `account_id` | `string` | Cloudflare account identifier used for Zero Trust resources. |
| `zone_id_pro` | `string` | Cloudflare zone ID for `atlasit.pro`, used by the firewall ruleset. |
| `zone_id_app` | `string` | Cloudflare zone ID for `atlasit.app` (reserved for future rulesets). |
| `dev_emails` | `list(string)` | Email addresses that should be allowed into the dev Zero Trust application. |
| `team_emails` | `list(string)` | Email addresses that should be allowed into the staging Zero Trust application. |

 
## Access policies with provider v5
Cloudflare provider v5 changes how Access policies are associated with applications:

- Policies intended for a specific application must be defined on the application resource itself via the `policies` attribute.
- The standalone `cloudflare_zero_trust_access_policy` resource is account-scoped and does not support `application_id` or `precedence`. Do not use it to attach app-specific rules.

 
Example (staging):

 
```hcl
resource "cloudflare_zero_trust_access_application" "stg" {
  account_id       = var.account_id
  name             = "stg.atlasit.app"
  domain           = "stg.atlasit.app"
  type             = "self_hosted"
  session_duration = "8h"

  policies = [
    {
      name       = "Staging Allowlist"
      decision   = "allow"
      precedence = 1
      include    = [for e in var.team_emails : { email = { email = e } }]
    },
    {
      name       = "Staging Deny All"
      decision   = "deny"
      precedence = 10000
      include    = [{ everyone = {} }]
    }
  ]
}
```

 
Migration note from v4 -> v5:

- Remove any `application_id`, `precedence`, or nested `application {}` blocks from `cloudflare_zero_trust_access_policy` resources.
- Move those policy definitions under the corresponding application’s `policies` list and set `precedence` there.

 
## Safe usage flow
 
1. **Format**: `terraform fmt -recursive`
2. **Validate**: `terraform validate` (or `npm run tf:validate` from the repo root)
3. **Plan**: `terraform plan` only. Review the output locally or on the PR comment generated by CI.
4. **Apply**: Only run after the plan has been reviewed and the manual `cloudflare-terraform-apply` workflow is approved by the required reviewers. Local `terraform apply` should be avoided unless break-glass access is documented.

The GitHub workflows keep plans non-destructive by default. CI never runs `terraform apply`; applying always goes through the manual workflow.

 
## Local examples
 
### terraform.tfvars
 
```hcl
# terraform.tfvars
api_token   = "<redacted-api-token>"
account_id  = "<your-account-id>"
zone_id_pro = "<atlasit.pro-zone-id>"
zone_id_app = "<atlasit.app-zone-id>"

dev_emails  = [
  "dev@example.com"
]

team_emails = [
  "teammate@example.com"
]
```

Run `terraform plan -var-file=terraform.tfvars` once the file is populated. Do not commit the tfvars file; add it to your local `.gitignore` if needed.

 
### Environment variables
You can also drive variables through the `TF_VAR_` convention:

```bash
export TF_VAR_api_token=$CLOUDFLARE_API_TOKEN
export TF_VAR_account_id=$CLOUDFLARE_ACCOUNT_ID
export TF_VAR_zone_id_pro=$CLOUDFLARE_ZONE_ID_PRO
export TF_VAR_zone_id_app=$CLOUDFLARE_ZONE_ID_APP
export TF_VAR_dev_emails='["dev@example.com"]'
export TF_VAR_team_emails='["teammate@example.com"]'

terraform init -input=false
terraform plan
```

Unset the variables after use if you are running from a shared terminal session.

 
## CI workflows
 
- `cloudflare-terraform-validate.yml`: runs `terraform fmt -check` and `terraform validate` for `infra/cloudflare` on every PR touching this path.
- `cloudflare-terraform-plan.yml`: produces a plan for pull requests, posting the diff back to the PR as a comment (no apply).
- `cloudflare-terraform-apply.yml`: manual `workflow_dispatch` that requires reviewer approval before running `terraform apply` (ensure the `cloudflare-apply` environment has required reviewers configured in repository settings).

Configure the following repository secrets (or environment variables scoped to the workflows) so that plans and applies have the data they need:
 
- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_ZONE_ID_PRO`
- `CLOUDFLARE_ZONE_ID_APP`
- `CLOUDFLARE_DEV_EMAILS_JSON` (e.g. `['dev@example.com']`)
- `CLOUDFLARE_TEAM_EMAILS_JSON` (e.g. `['teammate@example.com']`)

Document any deviations (such as temporary tokens or emergency applies) in the run logs and follow up by rotating credentials.
